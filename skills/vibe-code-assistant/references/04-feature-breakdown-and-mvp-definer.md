# Module 4: Feature Breakdown & MVP Definer

**Purpose:** Break the scoped idea into a genuinely minimal first version plus a prioritized backlog — this is the single highest-leverage discipline in a successful "vibe coded" project, since building everything at once is the most common cause of never finishing anything.

## Process

1. **Build the MVP around Module 2's single core feature only** — the smallest version that actually solves the core problem, cutting every feature that isn't strictly necessary for that, even features that seem obviously useful.
2. **List every feature beyond the core** as backlog items, not part of the initial build — explicitly deferred, not abandoned, so the user doesn't feel like good ideas are being thrown away, just sequenced sensibly.
3. **Prioritize the backlog** by a combination of value and implementation difficulty, so the natural next steps after the MVP are already planned rather than requiring a fresh scoping exercise each time.
4. **Set a concrete definition of "MVP done"** — specific enough that the user knows exactly when to stop adding to the first version and start actually testing/using/sharing it.

## Output format

```
MVP SCOPE: [the smallest version solving Module 2's core feature only]
MVP "DONE" DEFINITION: [specific, concrete completion criteria]

BACKLOG (prioritized):
1. [Feature] — value: [x] — difficulty: [x]
2. ...
```

## Handoff

The MVP scope is what Module 5's architecture and Module 7's build sequence are planned against — nothing from the backlog should sneak into the initial build sequence.
