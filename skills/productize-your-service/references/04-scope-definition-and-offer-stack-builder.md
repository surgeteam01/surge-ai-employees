# Module 4: Scope Definition & Offer Stack Builder

**Purpose:** Draw the single most important line in this entire skill — exactly what's included and excluded in the fixed package — and present that scope as a value-anchored stack. This is what actually makes a service "productized" rather than just "priced": a package with a fuzzy boundary will drift back into bespoke, re-quoted work within a few clients.

## Process

1. **List every component of the current bespoke service** (from Module 1), then sort each into: **always included** (core to every engagement, keep in the standard package), **sometimes requested** (from Module 3's common customization requests — decide explicitly: standard inclusion, priced add-on, or excluded entirely), and **rare/one-off** (explicitly excluded from the productized package; still handled as custom work at custom pricing if the business wants to keep that option open, but never silently absorbed into the fixed price).
2. **Write the scope boundary in plain, unambiguous language** — both what's included and what's explicitly not, since an unstated exclusion is exactly what causes scope creep. A good test: could a new team member read this boundary and know, without asking, whether a new client request falls inside or outside it?
3. **Set a turnaround time and deliverable format** for the standard scope — productized services typically win on predictability as much as price, so a vague "it depends" timeline undermines the whole premise.
4. **Assign an honest perceived value to each included component**, the same way a sales page's offer stack would, so the eventual price (Module 7) lands against a visible stack rather than a bare number.
5. **Flag scope items that conflict with Module 1's delivery capacity** — a scope that looks reasonable on paper but isn't deliverable at the stated turnaround given real team capacity is a problem to catch now, not after the first few sales.

## Output format

```
SCOPE BOUNDARY:
ALWAYS INCLUDED: [list]
STANDARD INCLUSION (from common requests): [list]
PRICED ADD-ON (from common requests): [list, with note on how it's priced separately]
EXPLICITLY EXCLUDED: [list — handled as custom work at custom pricing, if at all]

TURNAROUND TIME: [x]
DELIVERABLE FORMAT: [what the client actually receives]

OFFER STACK (within the included scope):
- [Component] — Value: $[x] — [one line: what it delivers]
(repeat)
TOTAL VALUE: $[sum]

CAPACITY FLAG: [any conflict between this scope/turnaround and Module 1's delivery capacity]
```

## Handoff

This scope boundary is a hard constraint for Module 8 (the delivery SOP must be buildable within exactly this scope) and Module 10 (the "what if I don't fit the box" objection is answered directly by how clearly this boundary is drawn). The offer stack feeds Module 6 (tier design) and Module 7 (price point calculation).
