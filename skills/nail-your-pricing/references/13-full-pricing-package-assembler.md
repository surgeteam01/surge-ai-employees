# Module 13: Full Pricing Package Assembler

**Purpose:** Assemble every prior module's output into one cohesive, ready-to-use pricing package — a presentable pricing page/sheet plus a companion script for live sales conversations — so the pipeline's output is something the user can put in front of a real buyer immediately.

## Process

1. **Assemble the presentation-facing package first**: the anchor, tier/price presentation, justification, guarantee, and CTA from Module 12, formatted as a standalone pricing page or sheet the user can publish or send directly.
2. **Assemble the sales-conversation companion**: the objection playbook from Module 9, the guarantee's full reasoning from Module 10, and the payment structure detail from Module 11, formatted as talking points a salesperson (or the business owner themselves) can reference live on a call — this is the material that doesn't belong on the public-facing page but absolutely needs to exist somewhere.
3. **Check consistency** between the two documents — the price, tiers, and payment options must match exactly between what's published and what's said out loud; a mismatch here is a fast way to lose trust with a buyer who compares the two.
4. **Check voice consistency** against the brief from Module 1 throughout the presentation-facing package.
5. **Verify nothing was lost**: the value stack, tier structure (if applicable), guarantee, payment options, and CTA should all be present in the presentation package, and the objection rebuttals should all be present in the companion script.

## Output format

```
=== PRICING PAGE / SHEET (publish or send directly) ===
[Full assembled presentation from Module 12]

=== SALES CONVERSATION COMPANION (internal use) ===
OBJECTION PLAYBOOK: [from Module 9]
GUARANTEE — FULL REASONING: [from Module 10]
PAYMENT STRUCTURE DETAIL: [from Module 11]
DISCOUNT POLICY REMINDER: [from Module 9 — what to say if asked for a discount]
```

## Handoff

This draft goes straight to Module 14 for scoring and optimization — don't present this as final without running it through the optimizer, since a first assembly pass can still carry a pricing decision that feels psychologically weak or a margin assumption worth double-checking one more time before it goes live.
